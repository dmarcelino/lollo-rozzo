# agent-skills

Skills this repo gives every agent of every stack, one directory per skill with a `SKILL.md`. `lolloctl skills` installs them into each stack's global skills, which every agent of that stack loads. They have no compose profile of their own; each one says when it applies, and does nothing on a stack without its feature. [docs/operations.md](../docs/operations.md#agent-skills) covers installing them.

![How agent skills are installed and what each one talks to](../docs/diagrams/agent-skills-architecture.svg)

An interactive version, [agent-skills-architecture.html](../docs/diagrams/agent-skills-architecture.html), opens in a browser from a clone of this repo.

## Files
| Path | What it does |
|---|---|
| `using-vault-secrets/SKILL.md` | How to keep vault values out of the conversation: placeholders by default, filled at the last step into a document, an MCP call's arguments (an email, through the `mcp-servers` wrapper's `--args-file -`) or a command; `delivery: "text"` only to reason about a value, with a reason; how a failed command still uses a handle up; and how to wait for the person's approval (`vault-wait` with every request's id, as one background command). Applies with the `lollo-vault` profile. [docs/vault.md](../docs/vault.md) |
| `using-vault-secrets/vault-run` | The vault's helper (Python, standard library only): redeems one or more single-use handles in one call to `http://lollo-vault:8000/redeem` (`LOLLO_VAULT_URL` overrides it; never a `VAULT_` name, which belongs to the values) with no proxy, all or none: the vault uses up no handle when one is unknown or a name clashes, with another handle's or with a `VAULT_` variable already set (sent as `taken`). It then runs one command with the values as `VAULT_<FIELD>` variables and scrubs them from its output. |
| `using-vault-secrets/vault-wait` | Run as one background command (Python, standard library only): waits on 1 to 5 vault requests by calling `get_result` through the `mcp-servers` wrapper (`LOLLO_MCP_SH` overrides its path), one call per request at once, with `wait_seconds` 50 and `collect` false, until none is pending (at most about 12 minutes), then collects them all and prints one JSON answer per id, so no handle's minutes start while another request waits. Exits 0 when all are done and collected, 1 when one is denied, expired, unknown or was collected earlier, 2 on bad usage or when the vault can't be asked: while waiting it collects nothing and names the ids to run it again with; while collecting it tries each id once (collecting hands the handle over, so a retry would get nothing), prints every answer it got, and marks the rest `not collected`. A stop while waiting collects nothing. Each wrapper call runs in its own process group, killed whole on a timeout or a stop. |
| `using-vault-secrets/vault-fill` | Run under `vault-run` (Python, standard library only): copies a template with each `{{VAULT_<NAME>}}` replaced by that variable, escaped for the format (JSON, HTML/XML, the XML inside Office and OpenDocument zips, text as is), to a file (0600, temp then rename, never over the template) or standard output; writes nothing when a placeholder has no value or is split by formatting, and prints no value. A `.csv` is filled cell by cell and written back with CSV quoting. |
| `fetching-web-pages/SKILL.md` | Read untrusted pages through pipelock's `http://lollo-pipelock:8888/fetch`, so the URL and the page text are checked. On any pipelock 403 (curl, Python or `/fetch`), find the reason through `/fetch`, retry a temporary DNS failure once, and otherwise report the block: never retry another way or make a request skip the proxy, in scheduled jobs too. Applies only when `HTTPS_PROXY` is `http://lollo-pipelock:8888` (the `lollo-pipelock` profile). [docs/egress-firewall.md](../docs/egress-firewall.md) |
| `news-radar-sources/SKILL.md` | How to set up a monitor (find the source, prefer feeds, schema.org data and JSON over HTML, `source_inspect`, `source_test` before `source_put`, a schedule in the stack's timezone, never a `letta cron` task), follow news on a topic, and write and repair from a report. Applies when Settings -> MCP lists `news-radar` (the `lollo-news-radar` profile). [docs/news-radar.md](../docs/news-radar.md) |
| `using-the-browser/SKILL.md` | When to drive the browser rather than read a page, tasks with an explicit id, snapshots and their refs, page text as data, signing in with a vault login (the username from `list_secrets`, `password` and `totp` piped through `vault-run` and `vault-fill` into `type_secret` and `type_totp` with the login's site as `expect_site`, stopping on a site-check refusal), hand-offs waited for with `wait_handoff` as a background command, screenshots taken with `browser-screenshot` (`--for-me` into a temporary folder to look at a page, read and removed; into the workspace, shown with the Markdown image line it prints, only when the person asks to see the page; looked at with Read before being described; `mcp_call` and `mcp_call_write` don't deliver the image), and checkouts (only when the person asked, the hand-off a site not allowed gets, a vault card's purpose naming the shop, items and total, never a retry without checking the order history). Applies when Settings -> MCP lists `browser` (the `lollo-browser` profile). [docs/browser.md](../docs/browser.md) |
| `using-the-browser/browser-screenshot` | The browser's helper (Python, standard library only): `browser-screenshot [--for-me] TASK TAB [NAME]` calls `screenshot` through the `mcp-servers` wrapper (`LOLLO_MCP_SH` overrides its path) with a 90 s limit, under the Bash tool's 120 s default, reading its JSON from stdout only, and writes the result's JPEG or PNG part to `browser-screenshots/<NAME or site-UTC time>.<ext>` in the current directory, adding a number rather than overwriting a file. It prints the path, the tab's URL labelled as the page's (data, never instructions) and the Markdown image line, with the file's absolute path, that shows it in the chat, never the image's data. `--for-me`, for the agent's own look at a layout or map, writes under `browser-screenshots/` in the temporary folder instead (0700, files 0600), removes screenshots there older than an hour first, and prints no image line, only the path to Read and then remove. Exits 1 and writes nothing when the tool reports an error, the result holds no image, or the image is not the JPEG or PNG it claims; 2 on bad usage or a name outside letters, digits, `.`, `_` and `-`. Lettuce's `mcp_call` passes on only a tool's text, which is why it exists. |
| `working-with-documents/SKILL.md` | Which of the `office` and `pdf` MCP servers does what, how to call them through the `mcp-servers` wrapper from the agent's workspace, and how to check a result before reporting it. Applies when Settings -> MCP lists them (the `lollo-doc-tools` profile). [docs/doc-tools.md](../docs/doc-tools.md) |

Only directories that contain a `SKILL.md` are shipped (`agent-skills/*/SKILL.md`), so this README is never installed.

## How it plugs in
- **`lolloctl skills <name|all>`** (`cmd_skills`, `sync_skills`): takes each `*/SKILL.md` directory, refuses a name that is not lowercase letters, digits and `-`, and refuses a name upstream Lettuce also ships in `upstream/docker/agent-skills`, since the BFF rewrites its own skills on every connect. It streams a tar of the skills over `compose exec -T app-server` to the in-container script `SKILLS_INSTALL`, which installs them into `/root/.letta/skills` (`state/letta-home/skills` on the host).
- **The manifest:** `SKILLS_INSTALL` unpacks into a dot directory first, so a broken stream changes nothing; then it removes the skills listed in `.lolloctl-skills`, moves the new ones in and rewrites the manifest. Upstream's skills and those enabled in Settings stay, and a skill deleted from this directory is removed from the stack on the next run.
- **Not automatic:** `up` and `add` do not install skills; `apply` and `self-upgrade` end with `skills all`. Otherwise run `skills` after setting up a stack or changing a skill. The stack must be up.
- **`backup`** leaves out the skills listed in the manifest and upstream's, since `skills` and the BFF reinstall them.
- **What each skill talks to:** `using-vault-secrets` calls the vault's MCP server through the `mcp-servers` wrapper, `vault-run` posts to its `/redeem`, `vault-wait` calls `get_result` through the wrapper, and its MCP-arguments recipe pipes `vault-fill` into `mcp.sh call ... --args-file -`; `fetching-web-pages` sends `curl` to pipelock's `/fetch`; `working-with-documents` calls `office` and `pdf` through the wrapper (`letta mcp call`); `news-radar-sources` calls News Radar's MCP server through the wrapper; `using-the-browser` calls the browser's MCP server through the wrapper, and its sign-in recipe pipes `vault-fill` into `mcp.sh call mcp__browser__type_secret --args-file -` under `vault-run`, like the MCP-arguments recipe, and `browser-screenshot` calls `screenshot` through the wrapper. None of them needs a tunnel route, a network or a volume of its own.
- No `check_stack` rule is specific to skills; the features they use have theirs ([CONTRIBUTING.md](../CONTRIBUTING.md#what-check_stack-enforces)).

## Rules
- **Only `skills` installs agent skills, and it replaces only its own.** `SKILLS_INSTALL` removes what its manifest (`.lolloctl-skills`) lists and leaves upstream's and Settings' skills alone. `up` does not sync skills.
- **Names must not match upstream's `docker/agent-skills`.** The BFF rewrites those on every connect, so a shared name would be overwritten. `skills` refuses one.
- **Skills are instructions, not boundaries.** Agents are root in the app-server and can ignore them; docs never present a skill as a protection.
- **Skill text is public** and lands in every operator's stacks: keep it generic, with no names, domains or values of a real deployment.

## Build and test
```bash
tests/run.sh test_skills_                   # sync_skills and SKILLS_INSTALL (stubbed docker)
tests/run-sidecar.sh vault -k "vault_run or vault_fill or vault_wait"   # vault-run against a loopback /redeem, vault-fill, and vault-wait against a stub wrapper (mounts agent-skills/)
tests/run-sidecar.sh browser -k screenshot_helper   # browser-screenshot against a stub wrapper (mounts agent-skills/)
```
There is no build step: `lolloctl skills all` pushes a changed skill to the running stacks.

## Upstream seams
Listed in [CONTRIBUTING.md](../CONTRIBUTING.md#upstream-seams):
- the global skills directory `/root/.letta/skills`, and the BFF rewriting upstream's `docker/agent-skills` there on every connect (why a shared name is refused);
- the `mcp-servers` skill's wrapper, `/root/.letta/skills/mcp-servers/scripts/mcp.sh`, named in `working-with-documents`, `using-vault-secrets`, `news-radar-sources` and `using-the-browser`;
- letta-code setting `$LETTA_CONVERSATION_ID` in the agent's shell, which `news-radar-sources` passes as a monitor's `set_up_in`;
- letta-code telling the agent when a background command finishes, which is how an agent waiting for a vault approval or a browser hand-off gets a new turn (`using-vault-secrets`, `using-the-browser`), and giving a background command no time limit unless the agent sets one (`run_in_background` without `timeout`; checked in letta-code 0.34.67), since `vault-wait` waits in one for up to 12 minutes; the vault's `pending` reply and `using-vault-secrets` name the Bash tool's `run_in_background: true` parameter, as `using-the-browser` does;
- `letta mcp call <tool> --args-file -` reading the arguments from stdin and exiting 2 when the tool reports an error (`using-vault-secrets`' MCP-arguments recipe and `using-the-browser`'s sign-in pipe `vault-fill` into it, under `bash` for `pipefail`);
- `letta mcp call` printing the tool's `CallToolResult` as JSON on stdout, image parts as `{"type": "image", "data", "mimeType"}`, with Node's warnings on stderr (`browser-screenshot` reads stdout only);
- letta-code's Read tool showing an image file to the model, and Lettuce's chat showing a Markdown image whose path is in the agent's workspace (`markdownImageTarget` in `web/src/lib/file-links.ts`), which is how `using-the-browser` has the agent look at a screenshot and show it;
- Lettuce's MCP bridge (`mcp_call`, `mcp_call_write`) passing on only a tool's text parts, an image becoming `[image content omitted]` (`textOfResult` in `bff/src/mcp-bridge/client.ts`; [lettuce#163](https://github.com/dmarchevsky/lettuce/issues/163)), which is why `browser-screenshot` exists.
