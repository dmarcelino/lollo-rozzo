# lib

The code behind `lolloctl`, the Bash CLI at the repo root. Admins run it from its published image, through a wrapper ([release/](../release/README.md)); developers run it from a clone. [DESIGN.md](DESIGN.md) is the design record of that split. `lolloctl` holds argument handling and one `cmd_*` function per subcommand, dispatched from `main`; it sources the two shell libraries here, and streams the Node script into a stack's app-server when it needs to change Settings -> MCP. No profile: the CLI runs on the host for every stack. The operator's guides are [docs/operations.md](../docs/operations.md) and [docs/cloudflare-setup.md](../docs/cloudflare-setup.md).

![lolloctl, its libraries and what they reach](../docs/diagrams/lolloctl-architecture.svg)

An interactive version, [lolloctl-architecture.html](../docs/diagrams/lolloctl-architecture.html), opens in a browser from a clone of this repo.

## Files
| File | What it does |
|---|---|
| `common.sh` | Messages (`info`, `warn`, `die`); the env-file helpers (`env_get`, `env_set`, `env_unset`, `cfg`); release mode (`release_mode`, `image_name`); paths and the data directory (`resolve_data_dir`); Lettuce's source and images (`fetch_upstream`, `upstream_image_ns`); the same-path check (`check_mounts`, `require_mounted`); `stacks.conf` (`conf_entries`, `conf_set`, `conf_unset`); validation of names, emails and profiles; the `compose`, `compose_env`, `compose_shared` and `host_docker` wrappers; doc-tools names and tags; VAPID keys, the notification tokens (`NOTIFY_SOURCES`) and the executor token; `stale_services`; and `check_stack` with its `check_*` helpers |
| `cloudflare.sh` | Cloudflare API v4: `cf_api` (curl + jq) and one `cf_*` helper per resource (Zero Trust team, Google login method, DNS lookup, Access policy and applications, tunnel, tunnel token, tunnel ingress, DNS CNAME); `PROFILE_ROUTES`, the lollo host's routes per profile, and the landing page's and the notifications page's routes |
| `mcp-servers.mjs` | Adds or removes one group of lolloctl's servers (`doc-tools`, `vault`, `news-radar` or `browser`) in the stack's shared MCP list. Node, no dependencies; never run on the host |
| `DESIGN.md` | Design record: installing without a clone (a published `lolloctl` image, published lollo images, the data directory, `stacks.conf` and `apply`) |

`lolloctl` sources `common.sh`, then `cloudflare.sh`; both expect `LOLLO_HOME` (the code) to be set and define functions only. `main` then sets `LOLLO_DATA` (`resolve_data_dir`) and, in release mode, runs `check_mounts` before any command.

## How it plugs in
- **`check_stack` gates every `up`.** It reads `stack.env`, renders the merged config and dies on the first unsafe setting. What it refuses, and which profile turns each check on: [CONTRIBUTING.md](../CONTRIBUTING.md#what-check_stack-enforces).
- **Cloudflare.** `cf_api METHOD PATH [BODY]` prints `.result`, or the API's errors and returns 1. `init`, `add`, `users`, `remove` and `profiles` call it; `up` never does.
- **The MCP list.** `mcp_servers` in `lolloctl` runs `compose NAME exec -T app-server node --input-type=module - add|remove FILE GROUP` with `mcp-servers.mjs` on stdin (the rules below).
- **Other writers of `stack.env`:** `up` (the push contact address, the executor token, the notifications service's keys and tokens, the browser's engine secret, `LOLLO_PROFILES`, and the admin's `NEWS_RADAR_*` settings copied from `config.env` by `sync_news_radar_settings`), `users` (`ALLOWED_USERS`, after the Access policy), `profiles` (`COMPOSE_PROFILES`, together with `config.env` `PROFILES`), and `mcp`, `add` and `up` (the MCP groups' markers). `init` writes `config.env`: the zone, account, Zero Trust team and Google login method ids, and `LETTA_IMAGE_NS` (as `upgrade` does). `add`, `users` and `remove` write `stacks.conf`.

## Rules

### Code and data are apart
`LOLLO_HOME` is the code: a clone, or `/opt/lollo-rozzo` in the image. `LOLLO_DATA` is the instance: `config.env`, `stacks.conf`, `.secrets/`, `upstream/<tag>/` and `stacks/`. Every path to the instance goes through `config_file`, `token_file`, `stack_dir`, `stack_env`, `stacks_conf` and `upstream_dir`; every path to the code through `LOLLO_HOME`. In release mode the wrapper passes `LOLLO_DATA`; from a clone it defaults to the clone's `data/`, so no clone or worktree reaches the real stacks by default, and a clone refuses a data directory a release runs (`bin/lolloctl` in it). `backup` and `receipts` refuse a destination inside either.

### Release mode is a file, not a setting
`$LOLLO_HOME/RELEASE` exists only in the published image (`publish.yml` writes it), so an admin cannot point a clone at published images by mistake. In release mode the overlays get each published image's name from it (`LOLLO_IMAGE_*`, through `compose_env`), `backup` and `receipts` use its names, and `check_images` refuses a lollo service that runs any other. From a clone, the same variables are unset and the overlays name the local builds, `lollo-<image>:local`.

### `up` builds only what is built on this host
`build_local_images` builds upstream's services when `config.env`'s `LETTA_IMAGE_NS` is empty (Lettuce publishes no images for this host), then the lollo's: from a clone all of them, in release mode only the code editor's shell. Two calls, in that order: the shell is built `FROM` the app-server's image by name (`APP_SERVER_IMAGE`, `docker-image://`), never `service:app-server`, which would rebuild a pulled app-server. Then `up -d --no-build --pull missing`: a published image that is missing fails rather than building from a context the image does not carry. Whether `LETTA_IMAGE_NS` is set is looked up by `init` and `upgrade` (`upstream_image_ns`), never by `up`. Only the registry's "manifest unknown" or "denied" means not published; any other failure stops the command and leaves `LETTA_IMAGE_NS` as it was, so an outage never switches every stack to building upstream's images.

### `up` never starts the browser without its sandbox
With `lollo-browser` on, `up_stack` starts the browser's engine alone, before the rest of the stack, and waits until it is healthy (`start_browser_engine`, `compose NAME up -d --wait lollo-browser-engine`). When it is not, it reads the engine's log: the line `lollo-browser-engine: Chromium's sandbox failed` (the launcher then exits 3) means the host's kernel or AppArmor keeps Chromium's sandbox from starting. Either way it stops the engine, so its restart policy does not loop, and fails, naming the host settings and the guide ([docs/browser.md](../docs/browser.md), "Running it"); the rest of the stack does not start. Nothing here, or anywhere else, starts Chromium without its sandbox, and `check_browser` refuses a stack whose engine would. `tests/run.sh test_up_refuses_the_browser_when_its_sandbox_fails` checks it.

### Every host path is the same inside lolloctl's container
Docker reads the paths lolloctl gives it on the host. A path mounted elsewhere in lolloctl's container would make Docker create an empty, root-owned directory in its place, and a stack would start without its data. In release mode `check_mounts` reads the container's own mounts (`docker inspect "$HOSTNAME"`) and refuses any bind mount whose source and destination differ, and a `LOLLO_DATA` that is not one of them or does not hold the wrapper (`bin/lolloctl`), which an empty directory Docker made cannot; it fails closed when it cannot find its container. It does not check the owner: the wrapper did, on the host, and inside Docker's VM on macOS a share can report another (Colima's virtiofs reports whoever looked first, root when Docker starts a container). `toolbox_personal` leaves the toolbox file's owner to the wrapper for the same reason. `require_mounted` refuses a `backup` or `receipts` destination, or a backup to `restore`, that the wrapper did not mount.

### `stacks.conf` is kept in step, and `apply` never removes
`apply` makes the stacks match `stacks.conf` through `add` and `users` (its update, `users_update`, without its `up`), then an `up` for each stack `add` did not just start, so none starts twice, each on its own so one that fails doesn't stop the others, and `skills all`. It never removes a stack and never changes a profile: it reports both, with the command to run. So that it never undoes them, `add` writes the stack's line as it starts (an interrupted add is resumed by `apply`), `users` rewrites it after the Access policy, and `remove` drops it once the name is confirmed (a stack Cloudflare could not fully delete is then reported, not set up again). A write that fails fails the command. An `add` that resumes takes the addresses it is given, updating the Access policy with `ALLOWED_USERS` if the policy exists, so an edit to `stacks.conf` between two tries is kept. `apply` runs each step in a subshell: one stack that fails does not keep the others from being set up and started, and `apply` fails at the end, naming the steps that did not finish. `stacks.conf` is parsed (`conf_entries`), never sourced.

### Env files are parsed, never sourced
`config.env` (global settings plus cached Cloudflare ids) and `stacks/<name>/stack.env` (that stack's secrets and Cloudflare ids) are plain `KEY=value` files that Docker Compose also reads. Sourcing one would run whatever it holds. Read and write them only with `env_get`, `env_set`, `env_unset` and `cfg`. `env_get` reads a key with awk (the last occurrence wins). `env_set` and `env_unset` rewrite the file through a temp file and `mv`, so the change is atomic and the file keeps mode 600. No quotes or inline comments in these files.

### Every Compose call goes through `compose`
Every `docker compose` call for a stack goes through `compose NAME ...`. It runs under `env -i`, so the caller's shell can't override `stack.env`. It passes the project `lollo-<name>`, `--project-directory upstream/docker`, the overlays in order, plus `compose/doc-tools.yml` and then `compose/pipelock-proxy.yml` when `COMPOSE_PROFILES` has `lollo-doc-tools` or `lollo-pipelock`, and an explicit `--env-file` ([compose/README.md](../compose/README.md) has the order). With `lollo-pipelock` it passes `PIPELOCK_DIRECT` (`config.env`'s list, then the stack's own, checked by `pipelock_direct`), which `pipelock-proxy.yml` appends to `NO_PROXY`. Whatever the profiles, it passes `LOLLO_DENY_HOSTS` (`deny_hosts`): the Lettuce host (`PUBLIC_ORIGIN`'s) and the lollo host (`LOLLO_HOSTNAME`) of every stack with a `stack.env` on this host and of the env file being rendered, and `<CF_TEAM_DOMAIN>.cloudflareaccess.com`, lower case, sorted and comma-separated. Every Compose call needs it, so a bad value never stops one: an entry that is not a host name, or an empty `CF_TEAM_DOMAIN`, is left out with a warning (a broken stack can still be looked at, stopped and removed), and `check_browser` refuses a stack whose own hosts are not host names; it dies only on more than 500. `compose/pipelock.yml` and `compose/browser.yml` hand it to `lollo-pipelock`, the browser's engine and `lollo-browser`, so an agent's browser task can never complete the person's Access sign-in ([browser/README.md](../browser/README.md#the-only-way-out-is-pipelock)). A stack added later reaches the other stacks' lists at their next `up`, which recreates their pipelock and browser (never the vault). With `lollo-doc-tools` it also passes `DOC_TOOLS_VOLUME` (`lollo-doc-tools-<tag>`, where `doc_tools_tag` hashes `doc-tools/` without its tests and README) and `DOC_TOOLS_NETWORK` (`lollo-doc-tools-<name>`) through `env -i`. lolloctl computes both; they are never written to `stack.env`. `compose_env ENV_FILE NAME ...` is the same with another env file: `check_stack --profiles` uses it to render a profile list before writing it. Plain `docker` calls go through `host_docker`, also under `env -i`.

### `stack.env` is the state record for `add` and `remove`
`cmd_add` creates the stack's Cloudflare resources in a fixed order and stores each id in `stack.env` as soon as it exists, so a failed run resumes where it stopped:

| # | Resource | Helper | Stored as |
|---|---|---|---|
| 1 | Access policy (the stack's people) | `cf_policy_create` | `CF_ACCESS_POLICY_ID` |
| 2 | Lettuce's Access application | `cf_app_create` | `CF_ACCESS_APP_ID`, `CF_ACCESS_AUD` |
| 3 | The lollo's Access application | `create_lollo_app` | `CF_LOLLO_APP_ID`, `CF_LOLLO_AUD` |
| 4 | Tunnel | `cf_tunnel_create` | `CF_TUNNEL_ID` |
| 5 | Tunnel token | `cf_tunnel_token` | `CLOUDFLARE_TUNNEL_TOKEN` |
| 6 | Tunnel ingress (routes) | `configure_tunnel` | nothing; reapplied on every run and every `profiles` |
| 7 | The lollo host's DNS CNAME | `create_lollo_dns` | `CF_LOLLO_DNS_RECORD_ID` |
| 8 | Lettuce's DNS CNAME | `cf_dns_cname_create` | `CF_DNS_RECORD_ID` |

`CF_DNS_RECORD_ID` comes last: once it is set the stack is complete, and `add` refuses to run again. Then `add` starts the stack (`up_stack`, `sync_executor`, `sync_doc_tools`) and registers its MCP groups.

`cmd_remove` stops the stack (`compose down -v`), removes its doc-tools network, then deletes in reverse: Lettuce's DNS record, the lollo's DNS record, the tunnel (after its connections; unsetting `CF_TUNNEL_ID` and `CLOUDFLARE_TUNNEL_TOKEN`), the lollo's Access application, Lettuce's, and the policy. Each id is unset only when its `DELETE` succeeds; the others stay in `stack.env`, so `remove` can be retried. `--purge` deletes the data only when nothing is left in Cloudflare. Tests assert the exact call order (`test_add_creates_everything_in_order`, `test_remove_*`): a new step keeps both orders. `up` makes no Cloudflare call.

### The Cloudflare API token never goes in argv
`cf_api` reads the token from `.secrets/cloudflare-api-token` and hands it to curl as a config block on stdin (`--config -`), so it never appears in argv, `ps` or shell history. Request bodies carry no secrets and go in argv. `test_init_never_puts_the_api_token_in_argv` checks it.

### Profiles change everywhere at once
All stacks share one app-server image, whose contents depend on the profiles, so the list is global. `cmd_profiles` first runs `check_stack NAME --profiles NEW` on every stack. That renders the config from a temporary copy of `stack.env` with the new list (through `compose_env`), so every check sees the new list. Only then does it write `config.env` `PROFILES` and every `stack.env` `COMPOSE_PROFILES` together, and run `up` on each stack. A stack that fails to start (its browser engine's sandbox refused by the host, a failed build) does not stop the others: since the lists are written already, a re-run would find nothing to change, so `profiles` goes on, skips that stack's executor and MCP sync (its `up` does both), and fails at the end naming `lolloctl up <name>` (or `up all` for several). An unchanged list skips all of that. It always removes `stale_services`: containers whose profile is off, which Compose leaves running. It compares what exists rather than what changed, so a re-run repairs an interrupted one. A stack that did not start keeps them: its old app-server still lists their servers in Settings -> MCP, so removing them would fail every `letta mcp tools` call until its `up`; the message then says to run the same command again after that `up`. Docs never tell operators to edit the lists by hand.

### Access policy and `ALLOWED_USERS` change together
Upstream requires the two to stay in sync, so `cmd_users` changes both.

### lolloctl owns the stack's Access applications' settings
Each stack has two Access applications, Lettuce's and the lollo's (`lollo-<name>-pages`, for `LOLLO_HOSTNAME`), sharing the stack's one policy, so `users` changes both. `cf_app_body` is the one definition of their settings. `add` posts it (`cf_app_create`), and `route_stack` puts it back on both on every `profiles` run (`cf_app_update`). A `PUT` replaces the application's settings, so a change made in the dashboard does not survive. Their cookie is HttpOnly, so no script on either origin (the code editor's tab included) can read the Access token and hand it to an agent, and SameSite=Lax. `check` does not read them back: it runs offline.

### Tunnel routes follow the profiles
- **Lettuce's host goes only to the app-server.** Every lollo page is on the lollo host, `LOLLO_HOSTNAME`.
- **The lollo host's name** comes from `pick_lollo_hostname`: `<label>-lollo.<domain>`, `<label>` being the first label of `LETTUCE_HOSTNAME`. A stack on its `HOSTNAME_FALLBACK` name therefore gets `lollo-<name>-lollo`. When that name is taken, it uses the first free of `<label>-lollo-2` to `-9`. `add` refuses new stack names ending in `-lollo`.
- **The rules, in order.** `cf_tunnel_configure` puts the lollo host's rules first:
  1. each route of `PROFILE_ROUTES` (`cloudflare.sh`) whose profile the stack has: `^/vault(/|$)` -> `lollo-vault:8000`, `^/gmail-triggers(/|$)` -> `lollo-gmail-triggers:8000`, `^/news-radar(/|$)` -> `lollo-news-radar:8000`, `^/code-server(/|$)` -> `lollo-code-server:8000`, `^/browser(/|$)` -> `lollo-browser:8000`;
  2. with `lollo-vault` or `lollo-browser` on (`notify_profiles`), the notifications page (`LOLLO_NOTIFICATIONS_PATH`, `^/notifications(/|$)`) -> `lollo-notifications:8000` (`LOLLO_NOTIFICATIONS_SERVICE`). Not a `PROFILE_ROUTES` row: a row has one profile, and its profile also feeds `LOLLO_PROFILES` and the landing page's links;
  3. with any of them on, the landing page and its assets (`LOLLO_LANDING_PATH`, `^/(assets/[^/]+)?$`) -> `landing:8000`. `landing` serves every asset under `/assets/`, so a new asset needs no route;
  4. a 404 for the rest of the lollo host, so `/executor/v1/`, the notifications service's send API (`/notify/v1/send`) and `/healthz` are never routed;
  5. then Lettuce's host -> `app-server:8080`.
- **`LOLLO_PROFILES`.** `up` writes it in `stack.env` (`sync_lollo_profiles`): the profiles of `PROFILE_ROUTES` that are on, in its order. Only `landing` gets it. Never pass `COMPOSE_PROFILES` or `LOLLO_PROFILES` to the other sidecars: any profile change would recreate them, and recreating the vault locks it.
- `add` sets the routes, and `profiles` re-applies every stack's routes on every run, before `up`. A new lollo sidecar adds a route: [CONTRIBUTING.md](../CONTRIBUTING.md#adding-a-lollo-sidecar).

### Google redirect URIs are manual
Google has no API for an OAuth client's redirect URIs. So with the `google` profile, `add` and `profiles` print each stack's URI, and `remove` reminds the operator to delete it (`google_redirect_uri`, `google_reminder`).

### VAPID keys are generated once per stack
A new keypair invalidates every device's push subscription made with the old one, so nothing makes a pair again once it exists. Two pairs, each held by one service:
- **Lettuce's BFF** (`PUSH_VAPID_*`): `add` writes it into the new `stack.env` (`push_env_lines`). `up` only keeps `PUSH_VAPID_CONTACT_EMAIL` in step with `config.env` (`sync_push_contact`).
- **The lollo's notifications service** (`LOLLO_VAPID_*`, only `lollo-notifications` gets the private key): `ensure_notify_secrets` makes it when missing, whatever the profiles, from `up_stack`, from `add` before it routes the tunnel, and from `profiles` before it checks a new list, so a stack made before it gets it on its first `up`. That stack's tunnel has no `/notifications/` route yet, and `up` makes no Cloudflare call: the `up` that makes the pair, with a sender on (`notify_profiles`), says to run `lolloctl profiles <the current list>` once (`notify_route_reminder`), which routes every stack and restarts none. `add` and `profiles` route it themselves and make the pair first, so their `up` says nothing; nor does a later `up`.

`check_stack` refuses a stack without either pair. The vault's and the browser's own pairs (`VAULT_VAPID_*`, `BROWSER_VAPID_*`) were retired once, when the notifications service took over their notifications: nothing makes or reads them, `check_stack` no longer requires them, and `up` leaves their lines in `stack.env` (a rollback finds them; a later release removes them).

### Each notification sender has a token of its own
`ensure_notify_secrets` also makes a token per sender (`NOTIFY_SOURCES`: `NOTIFY_TOKEN_VAULT`, `NOTIFY_TOKEN_BROWSER`, `NOTIFY_TOKEN_GMAIL_TRIGGERS`, `NOTIFY_TOKEN_NEWS_RADAR`; `openssl rand -hex 32`), each only when missing and whatever the profiles, so a sender turned on later finds its token. The values go into `stack.env` through `env_set`, never argv, and `check_notify_secrets` hands each to `jq` through its environment (`holders`), never `--arg`: any local user can read a process's argv in `ps`. `test_up_never_puts_the_notify_secrets_in_argv` logs `jq`'s arguments to check it. Compose gives each sender its own as `NOTIFY_TOKEN`, and `lollo-notifications` all of them. Whatever the profiles, `check_notify_secrets` refuses a token that is not 64 lowercase hex characters, two equal tokens or one equal to `LOLLO_EXECUTOR_TOKEN` (which agents can read), and any service but `lollo-notifications` and that sender whose rendered config holds a token's value (it would send as that sender), or any but `lollo-notifications` holding `LOLLO_VAPID_PRIVATE_KEY`. A token may be replaced: delete its line and run `lolloctl up`.

### The browser's engine secret is made once per stack
`BROWSER_ENGINE_SECRET` (32 random bytes in base64url: the path of the engine's control WebSocket, and its first 8 characters the display's password) came later, so `ensure_browser_secrets` makes it when missing, whatever the profiles, from `up_stack` and from `profiles` before it checks a new list, so a stack made before it can turn the browser on. Nothing rotates it; to replace it, delete its line and run `lolloctl up`. Only `lollo-browser` and the engine get it, and `check_stack` refuses the browser's profile with a malformed one.

### Upstream's version moves only through `upgrade`
`lolloctl upgrade <tag>` is the only way to move `LETTUCE_REF` (and `self-upgrade`, through it, to the tag a release was tested with, never back): Lettuce tags pin the letta-code server version the UI was compiled against. `fetch_upstream` downloads GitHub's archive of the tag into `upstream/<tag>.partial/` and renames it when complete, so `upstream/<tag>/` is always whole; `upgrade` removes the other tags once every stack is up. What to check on every upgrade: [CONTRIBUTING.md](../CONTRIBUTING.md#upgrading-lettuce_ref). In this repo, `config.env.example`'s `LETTUCE_REF` is the tag a release is tested with; Renovate proposes new tags there and merges a patch tag that keeps letta-code's version on its own ([Dependency updates](../CONTRIBUTING.md#dependency-updates)). An install still moves only through `upgrade`. After the move (or an `up all`, when the tag stays), `self-upgrade`'s `_after-upgrade` runs `skills all`, so a release's changed skills reach every stack.

### `restart`, never a single-service restart
The BFF shares the app-server's network namespace and dies when the app-server is recreated on its own, so `up` and `restart` act on the whole stack. The one exception is the BFF alone (`refresh_mcp_skill`), which leaves that namespace as it is.

### `toolbox` keeps the operator's credentials out of the stack
`toolbox` is a `docker run` of the stack's app-server image with one agent's workspace, never a `compose exec`: agents share the app-server as root, and the operator's tokens must not land where they can read them. The agent wrote the workspace, so it chooses neither what is mounted nor what runs with the operator's credentials.
- The agent id comes from the app-server, where agents are root: `find_agent` uses it only once it matches `^agent-[A-Za-z0-9-]{1,80}$` (`AGENT_ID_RE`, the landing service's pattern), for `shell` too. The toolbox mounts the fixed `state/workspaces` at `/work` and starts in `/work/<id>`, never a path built from the id, so a link the agent makes resolves inside the container, never on the host. A workspace, or `workspaces` directory, that is already a link is refused.
- Each operator credential is opt-in: `gh` (the GitHub token and git's credential helper), `ssh` (the ssh-agent) and `claude` (the Claude token and Claude Code's config, whose `settings.json` can hold secrets and hooks). A run chooses them by flag (`--gh`, `--ssh`, `--claude`) or by a `use` line in the toolbox file; `--no-credentials` ignores the `use` lines for one run. `~/.gitconfig` and `~/.ssh/known_hosts` are configuration, not credentials, and always come in, read-only. With nothing chosen, `toolbox` says how to choose.
- Before it starts, `toolbox_scan` looks at the workspace in a throwaway container of the same image: no network, read-only root, every capability dropped but `DAC_READ_SEARCH`, `no-new-privileges`, the workspaces read-only, no credential. Its script (`TOOLBOX_SCAN`, sent on stdin) parses `.git/config` with git's own parser, never follows a link (a link where a file would be read is a finding) and runs nothing it reads. It reports git keys outside an allow-list (which takes what submodules, linked worktrees, husky, `gh` forks and partial clones write), `ext::`/`fd::` remotes, `filter`/`diff`/`merge` drivers but Git LFS's, `.gitmodules` `update` commands, a `.git` file naming anything but its repository's `.git/modules` or `.git/worktrees` directory (whose configuration is read with that repository's), a `commondir` naming anything but its repository, and `.claude/`, `.mcp.json`, `.envrc` or `.npmrc` at the workspace's or a repository's root, to depth 6 (`node_modules`, `.venv`, `venv`, `vendor`, `target`, `build`, `dist`, `.next`, `__pycache__`, `.cache`, `.tox`, `.gradle`, `.mypy_cache` and `.git` pruned); hooks are not read, since `core.hooksPath` is forced (below); and  it reads repositories at any depth and in those folders too (a name-only search, bounded by 60 seconds; a folder that goes away during it is fine), and the same files in `/work` itself, above every workspace. A failed scan, one past 50,000 entries or repositories, or a repository search that does not finish, is a finding too. Findings stop the toolbox unless `--trust-workspace`. Widening the allow-list is a reviewed change.
- Whatever the workspace holds, and with `--trust-workspace` too, git in the toolbox gets `core.fsmonitor=false`, `core.hooksPath=/dev/null`, `core.sshCommand=ssh`, `protocol.ext.allow=never`, `core.pager=less` and an empty `credential.helper` (which empties the repository's list of helpers; gh's comes after it) in command scope (`GIT_CONFIG_COUNT`), which beats the repository's own config and the operator's `~/.gitconfig` alike, and `GIT_CEILING_DIRECTORIES=/work`, so git never takes the workspaces directory for a repository. An agent can still add configuration between the scan and the start (it can watch its workspace for reads), so the scan is a check, not a boundary: drivers with names it chooses and project files added after it are not covered.
- Tokens go through Docker's environment as `-e NAME`, never argv.
- The image's inherited `com.docker.compose.*` labels are emptied, on the toolbox and on its scan, or Compose and `stale_services` would count them as stack containers.
- `~/.config/lolloctl/toolbox` is parsed, never sourced.
- The agents' tools (`state/tools`) are mounted at `/opt/agent-tools` only with `--tools`, read-only unless `--tools=rw`. A missing directory is refused rather than created by Docker.
- In release mode the operator's home is `LOLLOCTL_HOST_HOME` (the wrapper mounts it read-only at the same path), and what only the host's commands can give (`gh auth token`, `secret-tool` or, on macOS, `security`, the toolbox file's `secret` lines) the wrapper runs on the host and passes as `LOLLOCTL_*` variables, by name. It reads the run's flags and the file's `use` lines with the same grammar as `cmd_toolbox`, and fetches, or forwards the ssh-agent for, only the credentials the run chose. A toolbox file `mount` that holds the data directory, or is inside it, is refused.

### Text from containers is printed inert
Agents write what lolloctl reads from a stack's containers: agent names, MCP server names, and the error output of its calls into the app-server. Before such text goes into a lolloctl message, `printable` (one line) or `printable_text` (keeping newlines and tabs) replaces every C0 control, DEL and C1 control with a visible `\xNN`, and every bidirectional override or isolate with `\u{NNNN}`, so it can neither drive the operator's terminal nor reorder a line. They work on code points with jq, so other non-ASCII text is left alone. Ids are compared before they are filtered. The non-interactive `compose exec` calls into the app-server (`find_agent`, `sync_skills`, the executor's install and removal, `mcp_servers`) go through `inert_stderr`, which holds their error output back and prints it through `printable_text`, keeping their exit status. Interactive sessions (`shell`, `toolbox`, `compose ... exec`) and `logs` pass through unchanged: the operator asked for them. Tests: `test_printable_*`.

### The runtime audit reads the state from outside the agents' reach and only reports
Agents are root in the app-server and write `letta-home`, so one injection can change lollo's own helpers (`vault-run`), drop a cron file, repoint an MCP entry or change the container's files, and keep doing so after every restart (SEC-002). `lolloctl audit` cannot stop that; it makes it visible. It never asks the app-server, whose binaries the agents control: never a `compose exec` or `docker exec` into the stack.
- **Where it reads.** The state from one container of the backup image (`BACKUP_RUN`: no network, read-only root) with `state/letta-home` mounted read-only at `/src`, running `AUDIT_SCAN` (bash, on stdin). The scan prints NUL-separated records that lolloctl parses, never sources: file hashes under lollo's skills, `lollo/executor/bin/` and every other skill and cron file, the entries of `skills/` and `system-cron/`, each cron file's first lines, and the MCP list (`MCP_SETTINGS`). It follows no link: a link is reported as one. Every list but lollo's own files is capped, with a note of how many were left out, so a flood cannot hide them. The container's own changes come from the daemon (`docker diff` of `compose ps -aq app-server`).
- **What it compares, on the host.** Lollo's skills file by file with the code's `agent-skills/` (`shipped_skills`), and the `.lolloctl-skills` manifest with their names (a hint only: `skills` replaces lollo's skills whatever it says). The executor's `run.mjs` with `landing/executor/run.mjs` and its cron file with `executor_cron`. Skills that are neither lollo's nor upstream's, cron files other than the executor's, and Settings -> MCP entries other than lollo's own (`AUDIT_MCP_URLS`, `AUDIT_MCP_COMMANDS`, held in step with `mcp-servers.mjs`'s `GROUPS` by `test_audit_mcp_list_matches_mcp_servers`), with an entry under one of lollo's names that is not lollo's called out. Container changes under `AUDIT_SENSITIVE` (cron, the loader's preload, shell start-up files, the binary directories and `/usr/local/lib`, where letta-code is installed) but the executor's cron file; `--verbose` lists every change.
- **Acceptances** are `stacks/<name>/audit-accepted`, outside the state the app-server mounts: `<sha256> <kind>:<key>` per line, written atomically at mode 600 by `audit <name> --accept` (`--unaccept` removes one). Each is bound to the entry's hash at the time, so a later change is reported again; for a `diff:` file or link that hash covers what the daemon's copy holds (`docker cp`, never exec: bytes, mode, owner, link target, not its time, since the entrypoint copies cron files again on every start), read for accepted entries only, so an accepted binary written again is reported again. Lollo's own skills and the executor are never accepted: `skills` and `up` put them back.
- **It never blocks.** `audit` exits 0 when it found nothing, 1 with findings and 2 when it could not audit (`all`: the highest). `status` (after each stack's table), `up` (in `up_stack`, before anything is recreated or the executor reinstalled), `skills` (before `sync_skills`) and `backup` (before the copy or any pause) run `audit_summary`, one line, and go on whatever it says. A stack never started has nothing to audit, and the scan never runs where `letta-home` is missing, since `run -v` would create it as root.
- Every name, path, cron line and MCP entry it prints goes through `printable` or `printable_text`.

Tests: `test_audit_*`, `test_up_audits_before_recreating`, `test_skills_audits_before_installing`, `test_status_prints_the_audit_summary`, `test_backup_goes_on_when_the_audit_fails`. [docs/incident-response.md](../docs/incident-response.md) is the operator's side.

### `mcp` registers the document tools, the vault, News Radar and the browser once per stack, and only those
There is no supported way to set Settings -> MCP across stacks, so `lolloctl mcp` is the one write into Lettuce's MCP list. It owns four kinds of entries and touches nothing else:
- **`doc-tools`** (profile `lollo-doc-tools`): entries whose command is under `/opt/lollo-doc-tools/`. It adds `office` and `pdf` when missing. A same-named server with another command is the person's and stays.
- **`vault`** (profile `lollo-vault`): HTTP entries whose URL is exactly `http://lollo-vault:8000/mcp`, under any name. It adds `{"name": "vault", "transport": "http", "url": "http://lollo-vault:8000/mcp"}` only when none is there, and nothing when another server is named `vault` (the person's). Registering the vault gives agents nothing new: they reach that URL over the stack network anyway, and approval stays in the vault.
- **`news-radar`** (profile `lollo-news-radar`): HTTP entries whose URL is exactly `http://lollo-news-radar:8000/mcp`, under any name, handled as the vault's (`httpGroup` in `mcp-servers.mjs`). It gives agents nothing new either: they reach that URL over the stack network anyway.
- **`browser`** (profile `lollo-browser`): HTTP entries whose URL is exactly `http://lollo-browser:8000/mcp`, under any name, handled as the vault's. A server of the person's named `browser` (Playwright MCP, say) stays, and nothing is added. It gives agents nothing new either: they reach that URL over the stack network anyway, and what limits them (the per-site settings, hand-offs, the vault's approval) is on the person's page and in the vault.

How it writes:
- `mcp-servers.mjs` is streamed into the app-server (the script on stdin) and touches only its group's entries.
- It refuses a file of any other shape.
- It writes a temp file, renamed only when the original is unchanged, and reads the file back after 2 s to catch an overwrite by the BFF (up to 4 tries).
- On a new stack it waits up to 90 s for the BFF to create the file.

When it runs:
- Success sets the group's marker in `stack.env` (`DOC_TOOLS_MCP_REGISTERED=1`, `VAULT_MCP_REGISTERED=1`, `NEWS_RADAR_MCP_REGISTERED=1`, `BROWSER_MCP_REGISTERED=1`; `MCP_GROUPS`, `MCP_PROFILE` and `MCP_MARKER` in `lolloctl`). `mcp` registers every group whose profile is on and skips a marked group unless `--force`, so a server the person removed stays removed. It refuses only when all four profiles are off.
- `add` registers a new stack's groups after `sync_doc_tools` (the document tools only when that succeeded). `profiles` and `up` never register.
- With a group's profile off, `up` and every `profiles` run remove that group's entries in each stack marked for it, and clear the mark. A stdio server that cannot start, or an HTTP server that does not answer, breaks every unfiltered `letta mcp tools` call. A failure keeps the mark, so the next run retries.
- Whenever a stack's list changed, `refresh_mcp_skill` restarts its BFF alone (`compose NAME restart --no-deps bff`), once per stack per command, so the `mcp-servers` description agents see names the new list. Its `stop_grace_period` lets a turn finish. A failed restart only warns.
- `add` and `profiles` say, for each group whose profile is on, whether each stack is registered, or print the entries and `lolloctl mcp <name>` (`mcp_reminder`).

## Build and test
No build step. Before changing the CLI, run `tests/run.sh` (or `tests/run.sh <pattern>`, e.g. `tests/run.sh test_add_`), shellcheck and, for `mcp-servers.mjs`, `node --test tests/mcp-servers.test.mjs` (for `scripts/check-doc-links.mjs`, `node --test tests/check-doc-links.test.mjs`); the exact commands are in [CONTRIBUTING.md](../CONTRIBUTING.md#building-and-testing). The curl stub fails on unknown routes, so a new Cloudflare call needs a route in `tests/stubs/curl`. [tests/README.md](../tests/README.md) describes the stubs and helpers.

## Upstream seams
- `mcp-servers.mjs`: the shape of the shared MCP list (`/root/.letta/mcp-home/.letta/settings.json`, one `agent-local-mcp-global` entry in `agents` whose `mcpServers` every `letta mcp` call reads), which the BFF renders whole, reads back from disk before every change, and shows as it is (so a person can see and remove our entries). A stdio entry with no args or env passes its validation, and so does the vault's `http` entry of only `name`, `transport` and `url`. Since Lettuce v0.50.0 the BFF moves any header an `http` entry carries out of the list, to `/app/data/mcp/credentials.json` on `bff-data`, on every connect (`ensureMcpServers`, `migrateFileHeaders`), and the `mcp-servers` wrapper then gets a 401 for that server: our entries must never carry headers.
- `common.sh`: `google_redirect_uri` assumes the BFF route `/api/google/oauth/callback`.
- `lolloctl`: `cmd_shell` assumes letta-code's memory path, `$LETTA_LOCAL_BACKEND_DIR/memfs/$AGENT_ID/memory`; `toolbox` the app-server image layout, `/opt/claude-code/bin`, and its workspace scan the image's `bash`, GNU `find` and `git` (`git config --file`, `--name-only`, `-z`); `find_agent` the JSON shape of `letta agents list` (`.items[]`); `audit` the MCP list's path and shape (`MCP_SETTINGS`), upstream's entrypoint copying `letta-home/system-cron` to `/etc/cron.d`, and letta-code's global install under `/usr/local/lib`.
- `check_stack` reads upstream's service names and volumes from the rendered config (`app-server`, `bff`, `channel-gateway`, `google-mcp`, `google-creds`).
- `app_server_image` assumes upstream names the app-server's image `${LETTA_IMAGE_NS}lettuce-app-server:<its release tag>`; `check_images` compares it with the render whenever the code editor's shell is built from it. `upstream_image_ns` assumes upstream publishes to `ghcr.io/<owner>/` and that `LETTA_IMAGE_NS` is its switch.
- `fetch_upstream` assumes GitHub's tag archives (`/archive/refs/tags/<tag>.tar.gz`, one top-level directory).
